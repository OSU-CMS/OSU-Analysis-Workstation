Short answer: maybe not, and the `summarize-signal-high-purity` output itself can't tell you either way — you need to go check what env vars the job actually ran with (or its log), because `DISAPPTRKS_REQUIRE_FIDUCIAL_MAPS` is not what turns the fiducial-map veto on.

Here's what's actually going on, from `ref/DisappTrks_Nano/pocket_coffea/workflow.py` (currently on the `MattDev` branch):

**`DISAPPTRKS_REQUIRE_FIDUCIAL_MAPS=1` is only a fail-loud guard, not a switch.** The electron/muon lepton-fiducial hot-spot veto is loaded from `DISAPPTRKS_ELECTRON_FIDUCIAL_MAP_JSON` / `DISAPPTRKS_MUON_FIDUCIAL_MAP_JSON` (or `DISAPPTRKS_FIDUCIAL_MAP_DIR`), independent of the `REQUIRE` flag. If a map path resolves and loads hot spots, it gets applied regardless of whether `REQUIRE_FIDUCIAL_MAPS` was set. If no path was configured at all, `_load_fiducial_hot_spots()` just returns an empty tuple and the job carries on silently with zero hot spots — `REQUIRE_FIDUCIAL_MAPS=1` is what would have turned that silent fallback into a hard error instead. So the real question isn't "did I set REQUIRE_FIDUCIAL_MAPS" but "did I also set `DISAPPTRKS_ELECTRON_FIDUCIAL_MAP_JSON`/`DISAPPTRKS_MUON_FIDUCIAL_MAP_JSON`/`DISAPPTRKS_FIDUCIAL_MAP_DIR` for that run?" If you didn't (and typically people set these together, which is presumably why you're second-guessing it), then the hot-spot veto was not applied at all, silently.

**In `signal_acceptance` mode specifically**, that hot-spot mask (when non-empty) gets ANDed directly into `search_mask` and `search_no_high_purity_mask` (workflow.py, right after the `if self._category_mode() == "signal_acceptance":` block) — i.e. into the pools that become `IsoTrackSearch`, `IsoTrackSearchNoHighPurity`, and `IsoTrackSearchHighPurity`. Those are exactly the categories `summarize-signal-high-purity` reads (`signal_selection_without_high_purity_*`, `signal_selection_with_high_purity_*`, and the `signal_cutflow_*` stages in `--full-cutflow`).

**Here's the part that makes this hard to check after the fact:** the printed `--full-cutflow` table has a row labeled "ECAL/electron/muon fiducial vetoes" (`track_fiducialECAL`), but that stage is a *different* thing — it's `tracks.isFiducialECALTrack`, a static per-track NanoAOD branch, unrelated to the dynamically-loaded lepton hot-spot maps. The lepton-fiducial-hot-spot veto controlled by `REQUIRE_FIDUCIAL_MAPS`/`*_FIDUCIAL_MAP_JSON` is folded into `search_mask` as a blanket AND *before* any of the labeled cutflow stages are built, so it never shows up as its own row. In other words: **there is no diagnostic in the `summarize-signal-high-purity` output — even with `--full-cutflow` — that tells you whether the lepton fiducial maps were actually loaded for that run.** You can't infer it from the numbers you already have.

**Does it actually matter for the highPurity decision?** The same hot-spot mask (present or absent) is applied identically to both the "without HP" and "with HP" pools, so the retained-fraction ratio that `summarize-signal-high-purity` reports is *not* automatically wrong — it's only biased if tracks that would have landed in a fiducial hot spot have a systematically different highPurity pass rate than tracks that wouldn't. That's plausible (hot spots are specific detector regions) but not something you can assume away, and it's exactly why the docs for this mode (`docs/pocket_coffea_workflows.md`, "Signal acceptance of the high-purity requirement") say to run with `DISAPPTRKS_REQUIRE_FIDUCIAL_MAPS=1` plus both `*_FIDUCIAL_MAP_JSON` paths explicitly, "so the tested selection matches the production search selection." Separately from the ratio question, if the maps were skipped, the absolute yields in both columns are inflated relative to the real analysis selection (they include tracks that production would reject), so anything downstream that uses the absolute numbers rather than just the retained fraction is off too.

**What I'd do before trusting this for the highPurity call:**
1. Check the actual environment/launch script (or Condor/log submission record) for that run to see whether `DISAPPTRKS_ELECTRON_FIDUCIAL_MAP_JSON`, `DISAPPTRKS_MUON_FIDUCIAL_MAP_JSON`, or `DISAPPTRKS_FIDUCIAL_MAP_DIR` were set — that's the thing that actually matters, not `REQUIRE_FIDUCIAL_MAPS`.
2. If you kept the job's stdout, grep it for `"fiducial-map hot spot(s)"` — the loader prints a line every time it successfully resolves a path or embedded hot-spot list (`Loaded N ... fiducial-map hot spot(s)`/`Opening ... fiducial map from ...`). No such line for electron or muon means no map was loaded and the run is missing the veto entirely (this would be true whether or not you set `REQUIRE_FIDUCIAL_MAPS`).
3. If neither map was configured, I wouldn't try to correct the existing numbers after the fact — I'd just rerun `signal_acceptance` with `DISAPPTRKS_REQUIRE_FIDUCIAL_MAPS=1` and both `*_FIDUCIAL_MAP_JSON` paths set, per the documented command. That also makes the run fail loudly instead of silently if something's misconfigured next time, so you don't end up back in this spot.

Bottom line: don't treat last week's `summarize-signal-high-purity` numbers as decision-ready until you've confirmed (from the launch config or the log, not from the output itself) that the electron and muon fiducial maps actually loaded. If they didn't, the safest path is a cheap rerun with the maps required, not trying to reason your way to a correction factor.
